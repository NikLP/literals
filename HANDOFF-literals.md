## Decisions already made (do not reopen)

- Standalone module `literals`, sibling of `aim` at `web/modules/custom/literals/`. No `aim_scope_literal`, no mirror of gists into `aim_fact`.
- `entity` scope stays (annotative facts about entities, ADR-0024). A literal is not a fact.
- The gist lives on the literal row. aim integration is a finder consumer: `aim_recall` calls `LiteralFinder` if the service exists (progressive enhancement), nothing stored in aim. An aim-stored-gist backend is a parked option.
- Finder (whole lookup) vs chooser (the model call). The finder filters by access, checks the outcome cache, then asks the chooser over the whole menu. No gate (removed 2026-10-05) and no vector DB or Search API.
- Chooser = Decision API `ChoiceQuestion` over key + gist only. Values never go to the model. Hosted Jev, demo data only.
- Base `literals` needs no AI. The finder (the chooser) is the optional, `drupal/ai`-dependent part: submodule or optional service.
- Pinned: moderation, aliases (field removed from the spike), pool sets, semantic cache, vector tier, staged choice.
- ADR-0039 is superseded by 0040.

The progressive-enhancement ladder (no model, decision model, large pools; what each costs and when to move up) is in [adr/progressive-enhancement.md](adr/progressive-enhancement.md).

## Current state (Phase 1 built, live on the DDEV site)

- **Model.** `literal` content entity (revisionable, published status, owner, created, changed; show_revision_ui, Gin sidebar layout via `hook_gin_content_form_routes`). Bundle = `literal_type` config entity (fieldable, `field_ui_base_route`). Fields: `name`, `key` (machine name generated from the name, unique across all literals), `value`, `gist` (short text, 255), `audience`.
- **Types and resolvers.** A type picks a `LiteralResolver` plugin (`text`, `token`, `entity`, `url`) and carries its settings (text: `validate_as` string/int/phone/email/url). Plugins validate on save (`LiteralValue` constraint) and `resolve($account)` at read time; `$literal->resolve()` is the single read call. `entity` stores `type:id` and resolves to its URL after a view-access check; `url` is **internal paths only** (starts with `/`, access checked; external URLs deliberately out until there is a reason, then an "allow external" type setting); `token` needs at least one known token.
- **Access.** One `audience` column: `anonymous` (everyone), `authenticated`, `restricted` (needs the `view restricted literals` permission). `LiteralAudience::visibleTo($account)` gives the matching set, used by the access handler and by a `hook_query_alter` on entity queries and Views, so lists never include a literal the viewer cannot open. Flat permissions: `administer literals`, `view restricted literals`, `create literals`, `edit literals`, `delete literals`. Pools no longer exist. Default audience is `authenticated` (fail closed).
- **UI.** Content > Literals is a view (`views.view.literals`) with exposed "Visible to" and Type filters, plus a `page_type` display at `admin/content/literals/type/%` (path kept for later). Structure > Literal types is the type UI. Value widget by resolver: URL gets a content title autocomplete (stores `/node/N`); token gets the Token module's browser if that module is installed (it is not on this site yet: `composer require drupal/token`).
- **Seed data on this site.** Types `text`, `phone`, `url`, `token`, `entity`; five throwaway literals. Config is exported to `config/sync` and the view is copied to `config/install` (no `uuid`/`_core`). `literals.info.yml` lists the view under `config_devel`.

## Phase 2 state

- **Reader.** `literals.reader` (`LiteralReader`): `load($key, $account)` (published revision only, `access('view')` for the account, missing and not-visible both give NULL) and `read(...)` (resolved value, cycle guard so token literals cannot loop). Bubbles `literal_list`, the entity's tags, and the access result's contexts.
- **Token `[literal:key]`.** `hook_token_info` lists published literals (reset on every literal save/delete); `hook_tokens` reads for `$options['literals_account']` if given (a token-resolver literal passes the asked account so a nested `[literal:x]` is not evaluated for the session user), else the current user. Unreadable gives nothing under `clear`. Keys that equal a literal field name or entity token (`url`, `name`, `value`, ...) are refused by validation: the Token module adds entity tokens under the same `literal` namespace.
- **Tool `literals:lookup`** (submodule `literals_tool`, needs `tool`): `key` (precedence) or `question` (uses `literals_finder.finder` if enabled, else a clear failure). Outputs `outcome` (match/ambiguous/none), `key`, `value` (empty unless match). Permission `use literal lookup tool`. Missing, draft and not-visible are one identical "none" answer. Renamed from the working name `literal_get`.
- **Guardrails.** Base constraint `LiteralGuardrails` on `gist` and `value`, no-op unless a `literals.guardrails` service exists (`literals_finder` provides it, set `literals_write_guardrails`: max length 2000, no HTML). The value is checked with `deterministic_only`: a model-backed guardrail added later still never sees a value. Runs at entity validation, so a programmatic writer must call `validate()` before `save()` (same as aim). The two guardrail configs trigger a schema warning about `check_all_messages` (same as aim's copy: upstream schema gap).
- **Audit.** `literals.settings:log_audit` (off). Writes (insert/update/delete) and reads log id/key/type/audience/uid/outcome, never gist or value.
- **Tests.** PHPUnit kernel tests in `tests/src/Kernel` and `modules/literals_tool/tests`: `ddev exec "cd /var/www/html && SIMPLETEST_DB='sqlite://localhost/sites/default/files/literals-test.sqlite' SIMPLETEST_BASE_URL=http://localhost vendor/bin/phpunit -c web/core web/modules/custom/literals/tests"` (about 2 minutes, separate processes). Covers audience/access matrix, query filtering, every resolver, reader, token, key rules, guardrail wiring, tool. Finder and guardrail runner are test doubles; the real finder is covered by `drush literals:eval`, not PHPUnit.
- Core's access handler memoizes per entity per request: a test that edits then re-reads in one process must `resetCache()` the handler.

## Search module and tool search mode (2026-10-05)

- `literals_search` (no AI, depends on `literals`): service `literals_search.search` (`search($text, $account, $limit)`: every word, up to 6, must appear in name, key or gist, case-insensitive, LIKE wildcards escaped; published only, audience filter in the query plus a per-entity view check, name order, drafts never, not even for admins); route `/literals/search/autocomplete` (permission `search literals`, JSON `{value: key, label: escaped name - gist}`, never values, cacheable on permissions, sign-in state and `q`). No scoring, no `search_api`: for a few hundred literals an entity query does it; swap in an index only for stemming, speed at thousands, or facets.
- `literals:lookup` tool: modes `key` > `question` > `search`. New output `candidates` ("key: name - gist" lines) for `search` and for an `ambiguous` question, so an agent can see what it is choosing between and then ask by key. Outcome `candidates` for search.
- Access caching fix: view access varied on `user` (per account); it now varies on `user.permissions` and `user.roles:authenticated`, which is all the rule depends on, so a page using `[literal:key]` no longer fragments per user. Tests assert both.
- The finder's cache fingerprint no longer includes the decision model ID (clear the cache when swapping models).
- **Context behavior with Jev (2026-10-05, seed 39 queries + 10 extra you/your queries written before the test).** Short site line and a longer 4-sentence version both: seed 29/29 hits and 10/10 none, extra 5/5 and 5/5 (so length is not a problem, and the extra set is a weak held-out check). A different medium ("library staff asking the IT helpdesk, so 'you' means the helpdesk, not the library") steered every "you/your" question to `none` (correct under that context: there is no helpdesk literal) but also lost "how can I call the library", which names the library explicitly: the negation ("not the library") over-steered. Never a wrong-confident pick in any variant: contexts push toward none, not toward wrong. Writing guidance: state who is asking positively, avoid "not X". Per-medium variants are therefore viable as the caller's `context` (replaces the site default); no registry built.
- Open: the guardrails runner still lives in `literals_finder` only because it needs `drupal/ai`; it could be its own module. The current site context text was written after seeing the failing query (see the behavior note above for what holds up).

## Phase 3 state (`modules/literals_finder`, needs `drupal/ai`; enabled on this site)

- **The embedding gate was removed 2026-10-05** (snapshot `pre-gate-removal` is from before; update hook `literals_finder_update_10001` dropped the `gist_vector`/`gist_vector_model` fields, the `literals_embed` queue and the `gate_*` settings; `literals:embed`, the embedder, worker and presave hook are gone). Reason: with a decision model it added no accuracy and, at 234 literals, no speed; alone it was a shortlister that could not say none (numbers in [adr/how-it-works.md](adr/how-it-works.md) and [adr/progressive-enhancement.md](adr/progressive-enhancement.md)). The code is in git history. Revisit only for menus past a few hundred literals with a measured need.
- Services: `literals_finder.finder` (`LiteralFinderInterface::find($question, $account, $context)` returns a `LiteralFindResult`: `match`/`ambiguous`/`none`, literals not values, plus tier `cache`/`chooser`/`pool` and a reason), `.chooser` (Decision API `ChoiceQuestion` over key + gist, `__none__` option, default `decision` provider from `ai.settings`), `literals.guardrails`. `logger.channel.literals` lives in the base module.
- Flow: candidates (published, audience filter in the query *and* `access('view')` per entity) > outcome cache (`cache.default`, key = question + audience set + admin flag + a fingerprint of the settings, context and decision model; tag `literal_list`; `none` cached `miss_ttl`s; errors never cached) > chooser over the whole menu. No decision model: `none` / `no_backend`.
- Chooser rule: argmax `none` is `none`; lead over the best *other literal* under `choice_margin` is `ambiguous`; below `match_threshold` is `none` (`low_confidence`). Settings `literals_finder.settings`: `match_threshold` 0.5, `choice_margin` 0.2, `miss_ttl`, `log_audit`, `chooser_context`, `chooser_instructions`. The thresholds are untuned placeholders that happened to hold on the gold sets.
- Eval: `drush literals:eval [file]` (default `eval/gold.seed.yml`, 29 answerable, 10 unanswerable, 9 seed literals incl. phone near-neighbours; `expect` may be a key, `none`, `ambiguous` or a list of acceptable answers). Scale pools: `eval/scale.gen.php.txt` (SCALE_N up to 225 synthetic `zz_` literals; instructions in its header). Hosted Jev, chooser over the full menu: seed 29/29, 10/10 none, 0 wrong-confident, 0.3 s/query; 60 and 234 literals 60/60, 10/10 none (3 repeat runs), 0.4 s/query.
- Lint: phpcs clean on the module; phpstan shows only `\Drupal::` service-location warnings.

- **Chooser context (2026-10-05).** Probing the chooser's probabilities showed "what is your phone number" was never a tie between the phones (the other two got 0): `__none__` won 0.92 because "your" names no one and the instruction says a wrong answer is worse than none. New setting `chooser_context` (prepended to the instructions; on this site: questions are put to the Harbourside Community Library, so "you"/"your" mean the library) moves it to main_phone at 0.91, keeps "phone number of the dentist", "of the council", "your email address" at none, and removed both scale false positives (3 repeat runs on the 234-literal pool: 60/60 hits, 10/10 none, 0 wrong-confident). Gold change, a decision to review: "what is your phone number" and bare "phone number" now expect `[main_phone, ambiguous]` (the `expect` field may be a list: a listed key or a tie is a hit, nothing is a miss, any other pick is wrong-confident); previously a bare "phone number" accepted only none/tie. Seed set with 9 new you/your phrasings: 29/29 hits, 10/10 none, 0 wrong-confident, 0.17 s/query. Caveat: the context text was written after seeing the failing query, and all numbers are on one gold set per site; the 9 added phrasings were written after the fix, so they are a weak held-out check. Where it cannot work: a site with no context line, or one whose owner is ambiguous ("you" in a multi-organization site), keeps the old behavior: none.
- **Gate on vs off and gate alone (2026-10-05), why it was removed.** With the decision model: seed pool 29/29 either way, 0.18 s gate on vs 0.31 s off (20 of 39 answered with no model call); 234-literal pool 60/60 either way, 0.44 s on vs 0.41 s off (5 of 70). Gate alone: seed margin 0.2 gives 17/29 hits, 12 tie lists, 0 wrong, 3 of 10 unanswerable get candidates instead of none; margin 0.1/0.05 pick wrong or leave false positives; the synthetic pool is lexically easy (margin 0.05 60/60, 5/10 unanswerable not none). A split into an optional `literals_gate` module was considered and dropped in favor of removal. `match_threshold` sweep (0.5 to 0.95) did not fix the near-topic false positives; the context line did.
- **Cache key fix and per-call context (2026-10-05).** The finder's outcome cache was keyed on question + audiences only, so a changed `chooser_context`, instructions, threshold, gate state or decision model kept serving old matches (matches never expire). The key now includes a fingerprint of those settings plus the call's context. `LiteralFinderInterface::find($question, $account, $context)` and `LiteralChooserInterface::choose($question, $candidates, $context)` take an optional per-call context that replaces the site default for that lookup (same site, different asker/role/purpose). Verified live: different context calls the chooser, same context hits the cache, a changed site context is not served stale. Context is a hint, not a filter: a "bakery" context still returned the library's only main phone. The tool does not expose `context` yet (an MCP caller could steer the chooser prompt; pool and access filtering still bound what it can return).
- **Pinned, not built:** merge a missed question into the gist (consolidation-style: model proposes, verifier checks, person approves), ADR-0040 Addendum 8. An alias-field version was built and fully removed 2026-10-05 (it was not asked for). Aliases reconsidered 2026-10-06 (ADR-0040 Addendum 9): the plain-text `ALSO` gist convention tested 9/9 on invented names with no field or parser; gist stays 255; groups (carrying audience, narrowing the pool) are the open design.
- Full explanation with efficacy table: [adr/how-it-works.md](adr/how-it-works.md).

## Parked ideas (from the 2026-10-05 thread; not started, none urgent)

- **Guardrails as its own module (`literals_guardrails`).** Today the write-guardrails runner (`LiteralGuardrails`, service `literals.guardrails`, the `literals_write_guardrails` set with its max-length and no-markup guardrails) lives in `literals_finder` only because it needs `drupal/ai`. It has nothing to do with finding, so a site that wants Guardrails at save but no chooser must install the finder. Split would move: `LiteralGuardrails`, its services entry, and the three `ai.ai_guardrail*` configs (their `enforced` module dependency changes), and give the new module `ai:ai` and `literals:literals`. The base constraint (`LiteralGuardrails`) and the `LiteralGuardrailsInterface` stay in `literals` and need no change (they already look the service up optionally). Needs an update hook or reinstall because the configs move owner. Keep the rule: a literal's value is only ever checked by deterministic guardrails (`deterministic_only`).
- **Chopping a large pool before the chooser** (only if a pool outgrows the full menu; the full menu held at 234 literals with no loss): (a) narrow by literal type at call time (free, deterministic; the type is already a grouping); (b) an optional group field and narrow by it; (c) staged choice: choose the group, then the literal (two sequential model calls, still only `drupal/ai`); (d) a keyword shortlist from an index into the chooser (drops paraphrases the model would have caught; that is why the embedding gate existed, and it did not pay at 234). Measure before building any of them.
- **`search_api` behind `literals_search`.** The search is a plain entity query (name, key and gist, every word must appear). An index would add stemming, speed at thousands and facets; swap it in behind the same `literals_search.search` service. Not needed at a few hundred.
- **Keyword baseline for question lookup** (a score floor and margin over the keyword hits) was not run and is not built; `literals_search` deliberately lists candidates and never decides.
- **Per-medium named contexts.** The per-call `context` already works (a chat widget, an agent and a staff form can each pass their own; it replaces the site default). A registry of named contexts is only worth building once a second consumer exists. Write contexts positively: a negation over-steered.
- **Local in-house Jev models** are expected soon. When one exists, re-measure the chooser (latency, accuracy, 50 to 500 options) before deciding whether any pool-chopping or gate is needed; clear the finder cache when swapping models (the cache fingerprint deliberately does not include the model).
- **Finder module name.** `literals_finder` stays (finder = access filter, cache, chooser); a rename to `literals_chooser` was considered and dropped as churn.

## Decisions made this session (do not reopen)

- Bundle is the **type** (config entity, resolver plugin), not the pool. A literal holds one value; resolvers replace per-literal "validate as".
- Access is data on the row (`audience`), not per-pool permissions. A scope-plugin interface (`checkViewAccess()` plus a query-condition method, aligned with aim's scope types) is the next step only when a second scope is needed; per-type "restricted" permissions are the likely first extension.
- Token form is `[literal:key]` (keys are global), not `[literal:pool:key]` as the ADR text says.

## Gotchas and housekeeping

- `literals.module` only holds the `literals_audience_options()` allowed-values callback.
- **Changing the entity definition on this site.** There is no migration story yet. Field changes went through `hook_update_N` (see `literals.install`); a bundle-key change needed `drush pmu literals` and re-enable (remove the view from `config/install` first, then rebuild the view from the exported YAML). Uninstalling a field that targets a removed entity type fails: keep the old class until the update runs.
- **Never hand-type `dependencies` or `cache_metadata`.** Save through the API, export, copy to `config/install` minus `uuid`/`_core`.
- **config_devel is installed (--dev).** `drush config:devel-export literals` (`cde`); entity IDs under `config_devel: install:` in `literals.info.yml`. Config schema checks: validate with `\Drupal::service('config.typed')->createFromNameAndData($name, $data)->validate()` (`config:inspect` is not available).
- **Drush scripts** run as anonymous: set `\Drupal::currentUser()->setAccount(User::load(1))` first. `drush php:script` only sees files inside the project (the container cannot read `/tmp`); put scratch scripts in the site root with absolute `/var/www/html/...` paths and delete them. Do not name a function `t()`.
- Core's validator context takes typed data only; use core constraint plugins via the `validation.constraint` manager, not raw Symfony constraints.
- `key` is an SQL reserved word as a column name; it works, but watch it in raw queries.
- **Config sync parity:** keep `config/sync` matching the DB (`drush config:status`, then `config:export -y`) or a stale `drush cim` uninstalls the module. Snapshot `pre-literals-spike` is from before the module.
- Project rules (CLAUDE.md): no em dashes, no auto-commit, American English, run phpcs (`ddev exec "cd /var/www/html && vendor/bin/phpcs --standard=Drupal,DrupalPractice web/modules/custom/literals --extensions=php,module,inc,install,yml"`) and phpstan before calling PHP work done.
